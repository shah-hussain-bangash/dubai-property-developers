MANUAL REPLY AND CALLBACK DASHBOARD - STEP 637

Prospect Research now includes the shortcut Go to replies and callback tasks,
and section 5. Replies and callback tasks at the bottom of the page. Loading this
panel is explicit and read-only; it does not read an inbox or run a search.

Click Load replies and tasks. Choose a saved prospect, channel, classification,
received time in your device's local time, and paste the actual reply text. Check
the prospect match and classification confirmation before Save manually recorded
reply. Record an opt-out as Opt-out, not an ordinary reply. Automatic replies and
bounces have separate classifications. This is human classification, not AI.

An ordinary reply creates or updates a human callback review task assigned to the
signed-in user. Notifications remain local records labelled undelivered; no email
is sent to the owner. Calling permission stays unknown, and no call is placed.
Opt-outs persist suppression and cancel pending callbacks atomically. An archived
or suppressed prospect does not receive a new callback task. Existing step635/636
rules and transactional tenant/revision guards remain authoritative.

The assigned user can Record human outcome, choose completed or cancelled, and
save a note. This records a human action; it does not initiate a call or meeting.
The queue shows tasks in groups of 20. All tasks can be shown. The latest 50 reply
previews show up to 500 characters each; the bounded full evidence stays in storage.
Untrusted message text is rendered as text, never HTML or executable instructions.

No request is sent on panel mount. Drafts remain in memory, not browser storage.
After any uncertain action, further writes are blocked until an explicit reload.
The manual event ID stays with the draft through reload, so an exact retry is
idempotent. Do not change a draft whose save might already have committed; inspect
the reloaded history first. Refreshing/closing the browser can discard an unsaved
draft. Mutating buttons are guarded against double clicks; no automatic retries.

API: GET/POST /api/v1/prospect-research/replies and POST /replies/close-task.
Read/write permissions, isolated local research settings and browser origin rules
match existing prospect routes. Server principal determines tenant and owner.
Client owner/tenant claims and unconfirmed matches are refused. Requests are size
bounded, timestamps must be aware and not in the future, and errors are sanitized.
No webhook, sending operation or provider inbox adapter is registered.

INSTALLATION AND RUNNER HANDOFF
This update needs new API/dashboard images. Stop the terminal research runner
with Ctrl+C before running step637_apply.ps1. Its saved PostgreSQL job survives.
The refresh acquires the same per-job Windows locks as the runner and refuses to
refresh while a known saved job is open in another runner. It holds these locks
through the build and refresh. Do not create/start new research jobs during this
refresh. If the saved job list changes, refresh stops before recreating services.

The existing SerpApi configuration is preserved through masked private key entry
when configured, using the accepted child-environment method. Never paste a key
into chat. Only API/dashboard are refreshed; PostgreSQL and Redis keep running.
Fictional in-memory demo records reset; saved prospects, reply history and jobs
remain in PostgreSQL. No job is advanced or real reply inserted by checks.

After PASS, run step637_start_research.ps1 and select your job. This updated
launcher verifies the current application sources; the older step634 launcher
checks historical hashes and will refuse after this update. Existing quota_wait
and query checkpoints are retained; the daily search limit remains 1. Restarting
the runner is explicit and the installer does not start searches for you.

Still not connected: automatic inbox sync, real owner/agent notification delivery,
email/WhatsApp outreach, automatic calls or meeting booking. This stage is a
manual, locally authenticated reply-review workspace.
