Step648 - Controlled property publication and connected public catalogue

Agent Portal > Website listings prepares a separate public property version. Existing
properties, private descriptions and photos are never published automatically. Agents
must be approved, own the property, set it Available, write public copy (80-4000
characters), choose 1-6 photos and confirm accuracy and permission to publish.
Title, location, type, purpose, asking price, bedrooms, bathrooms, area and reference
are taken from the current private property version. Private description is not copied.
Review all these fields for personal information before submission.

Admin > Website listing review inspects the exact public snapshot and metadata-stripped
photo previews. Explicit confirmation is required to approve and publish. Admin can
return a pending submission for changes or withdraw it. An approved owner can withdraw
their own submission. Public responses contain only an explicit field allowlist;
agent IDs, account details, private notes and internal review feedback are excluded.
Approval is permission to display; it is not independent title, permit or investment
verification. Obtain the necessary rights and listing permissions before publication.

The public website Properties menu opens /catalogue, with real published records only,
location/text search, purpose/type/budget filters, sorting and pagination. /catalogue/ID
shows selected photos, public description and a property enquiry link. No fictional
stock listings or made-up metrics populate this catalogue. Homepage inspiration cards
and current-offers imagery retain their illustrative status.

A property edit (even private notes), photo change, status change or Trash move changes
the private version and immediately hides the approved public version and photo routes.
The agent must resubmit the current version and Admin approve again. Resubmitting a
published property hides the old publication while pending review. Agent access
revocation withdraws pending/published submissions; reapproval never republishes them.
Revision checks reject stale edits/reviews. Property ownership, approval and visibility
are enforced on the server under the same private-store lock, including photo reads.
Previously downloaded copies cannot be recalled by withdrawal. Responses use no-store.

Public still JPEG/PNG/WebP responses remove embedded metadata containers. Private
original files remain intact. Animation and unsupported container structures fail
closed. This is bounded container sanitisation, not a full pixel decoder, image
reconstruction or automated visible-redaction service. It does not detect text,
watermarks, faces, addresses or private information visible in pixels. Metadata removal
may affect orientation/colour; review sanitised previews before publishing. Unknown
critical PNG/JPEG structures and invalid file lengths are rejected. Source format
references: https://www.w3.org/TR/png/ and
https://developers.google.com/speed/webp/docs/riff_container

Property enquiry links load the current public listing on the server, show its title
and reference read-only, then validate its publication version again at submission.
The shared inbox stores server-derived property ID, reference, title, asking price,
purpose, publication and property versions. Withdrawn or changed versions return a
refresh error without saving a new enquiry. Receipt retries remain idempotent even if
the listing later disappears. General enquiries and authorised intake bridges retain
their existing flow. No automatic agent assignment, notification, provider sync,
reservation, outbound email, WhatsApp message or call is added.

Optional publication and enquiry context fields remain backward compatible with old
private stores and are validated when read or included in encrypted recovery snapshots.
The same private JSON store capacity and local deployment limits apply. No database
migration, background publication or new account is performed at install.

Install step648_apply.ps1 after Step647 is installed and serving. Guarded backups,
full application tests, strict TypeScript and six offline refresh simulations precede
a dashboard-only refresh. Owner sign-in, accounts, API, researcher, PostgreSQL, Redis,
search configuration and33 held reviews remain. No password or provider-key entry.
This exposes an unauthenticated catalogue only on the existing local website; it is
not an internet launch. Production hosting/TLS, backend identity, regulatory review,
email verification/reset/MFA and native external integrations remain separate work.
