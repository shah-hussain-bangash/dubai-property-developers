Step646 - Portal recovery foundation (first production-readiness release)

Admin > Portal recovery (/recovery) creates an encrypted .dpdbackup download and
runs an isolated restore check. Existing accounts and source backups are preserved.
This is not an internet deployment and not a complete disaster-recovery system yet.

Coverage: member identity/password hashes, agent access, properties including Trash,
referenced private photos, enquiries, clients, planner tasks, activity, saved views,
source-bridge configuration/digests and encrypted owner email/password-hash config.
No plaintext owner configuration is returned. Active owner/member sessions, login
attempts and unfinished public enquiry tickets are excluded. Unknown/unreferenced
files and unreferenced photo files are not included. PostgreSQL research, Redis,
external CRM/mailbox/provider state and infrastructure secrets are outside this archive.
Keep existing PostgreSQL backup/recovery procedures and cover both data stores.

Create: sign in as Admin; use a unique16-128 character backup passphrase, confirm it,
download the encrypted file, and store file and passphrase separately and privately.
The project does not save or recover that passphrase. Do not use your Gmail password.
AES-256-GCM authenticates ciphertext and version header. A random16-byte salt,
random12-byte nonce and scrypt N32768/r8/p3 derive a256-bit encryption key.
The encrypted payload contains an allowlisted, hashed manifest. Snapshot locks cover
member and property state; live sessions are not restored. A lock heartbeat prevents
long snapshot reads looking stale to normal application writers. Busy snapshots fail
rather than bypassing the live lock. No external network requests are made.

Restore check: choose the downloaded file and its passphrase. Authentication is
verified before parsing; all requests are bounded. Decrypt and validate the format,
file sizes/hashes, record schemas, password hash syntax, photo references and raster
signatures. Refuse path traversal, duplicate/unreferenced entries, live sessions,
invalid hashes, missing photos, corrupted records and unsupported formats.
Write only inside a newly-created temporary directory, read back and verify each
file, then remove that directory. No live portal file or owner setting is overwritten.
A successful result reports counts, archive date and liveRecordsChanged=false.
No raw credentials, record content, session tokens or decrypted files are returned.

The encoded JSON payload limit is64 MiB, before encryption; each photo remains
bounded by the existing2 MiB rule. Oversize snapshots are refused, never truncated.
This memory-bounded release is for the local portal. Larger datasets require an
operator-managed encrypted volume backup/streaming storage design. Archive keys and
passphrases must not be shared in chat, email logs or source control.
No retention scheduler or automatic off-computer backup is installed by this release.

Recovery limitations: this verifies unpacking and schema/photo integrity, not restored
application startup, all business referential links, PostgreSQL recovery, mailbox access
or a real disaster recovery cutover. A controlled full restore remains separate work:
isolate/stage a matching application version, recover owner config privately, restore
volumes under maintenance, invalidate sessions, review bridge keys, verify all required
business journeys, and only then approve cutover. Do not copy decrypted files into a
running portal or overwrite its files manually from an unverified archive.

Account changes: existing strict member storage validation is shared with recovery,
including rejection of duplicate member IDs/emails. It never resets invalid files.
Portal property storage validation is shared, keeping prior validation behaviour.
No password reset, email verification, MFA or provider connection is enabled here.
Those remain subsequent milestones, alongside real inventory publication and CRM sync.

Installation: run step646_apply.ps1 after Step645 installed and serving. Guarded source
backups, all current frontend tests, recovery checks, strict TypeScript and six offline
refresh simulations run before dashboard-only refresh. Existing owner password/hash,
API, PostgreSQL, Redis, research settings, researcher and33 review holds are preserved.
No actual business-data backup is created automatically by install or health checks.
