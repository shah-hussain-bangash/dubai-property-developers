PERSISTENT REPLY AND CALLBACK STORAGE - STEP 636

This stage installs the transactional reply storage adapter and provisions one
dedicated PostgreSQL table, prospect_reply_workspaces_v1. Existing prospects,
research jobs, search settings and service processes are preserved. No real
replies, tasks or notifications are inserted by installation or acceptance checks.

Each active organization has a separately validated reply workspace and revision.
Its JSONB snapshot stores reply evidence, human callback tasks, unsent notification
records and opt-outs together. The organization UUID foreign key, positive
revision constraint and active-organization lookup enforce storage identity.
Organization row locking serializes writers, including first insertion. Revision
checks prevent stale updates. Each mutation uses the caller's transaction; the
adapter never commits a partial reply, task, alert or suppression on its own.

record_incoming requires an already authenticated/classified/matched event. It
loads the prospect from that organization's existing prospect workspace and
derives archive status there, instead of trusting a caller's archive claim. It
never guesses a person from an email/name/phone and rejects unknown prospects.
The integrating API must authorize the owner assignment and incoming event before
calling it. No exposed route, webhook, account connection or owner lookup exists
in this stage. Client claims are not an authentication boundary.

An exact event replay returns unchanged persisted state without incrementing the
revision, including when the replay carries an older revision. A replay that
changes content or attribution fails. New events with stale revisions fail.
The step635 rules govern task reuse, human review, opt-outs and permission status.
An opt-out and cancellation of pending callback tasks commit atomically. Messages
are untrusted text and must be escaped in any future display.

read_replies is read-only. An organization without a reply snapshot returns empty
state at revision zero without inserting a row. ISO timestamps restore through
strict JSON validation. Corrupt tenant identity, fingerprints or task attribution
fail closed. close_callback requires the assigned owner and current revision.
No whole-state overwrite, sending operation or automatic call entry point exists.

INSTALLATION
Run step636_apply.ps1 in the second terminal. It verifies protected inputs and all
33 review holds, installs only new sources, and runs 53 offline rule/storage tests
plus seven simulated provisioning checks. No API/dashboard rebuild is requested.

The launcher verifies the existing local Compose API/dashboard/PostgreSQL ports
and project directory. It starts a separate short-lived Python interpreter inside
the running API container using docker exec. Two verified modules travel through
stdin into that interpreter only; no files or API process modules are replaced.
The existing database configuration stays inside the container. No provider key
is printed, passed from the host or requested again.

That interpreter provisions only the dedicated reply table, checks its columns,
types, primary/foreign keys and revision constraint, and performs a read check.
It does not create organizations or alter existing tables. Subsequent runs use a
check-only read, preserving the first successful provisioning evidence. Container
identity and search capabilities are checked before/after. No service restart,
search, source fetch, inbox fetch, alert, call or live callback is requested.

The existing research runner may remain open. It still observes the shared daily
search quota. This storage stage does not make research run faster.

NOT YET CONNECTED
Reply-review dashboard/API, durable inbound provider adapters, real owner alert
delivery, mailbox/WhatsApp synchronization and calling. Notifications remain
not_connected records, and callback tasks need human review with calling permission
unknown. Provisioning an empty table does not enable those integrations. A later
API image refresh will be required to expose the installed adapter to live routes.
