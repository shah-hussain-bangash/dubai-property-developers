Step649 - Separate local n8n for authorised lead workflows



Run step649_apply.ps1 in your project terminal. It installs only the optional n8n

setup files, runs28 offline tests and starts a separate Docker Compose project named

dpd-n8n-local. No dashboard/API rebuild, provider-key prompt or property-service

restart is requested. The researcher can keep running. If you already use hosted n8n,

keep that setup instead; installing this optional local instance is not required.



A fixed official n8n release (2.45.5) is pulled from docker.n8n.io/n8nio/n8n. Its

registry digest is saved in step649_n8n_image_pin.json and the service is started using

that immutable digest. Re-running never upgrades an existing service to a newer tag.

This is not a cryptographic signature verification or a security certification of n8n.

The current vendor release was checked on2026-10-28. Future upgrades need review.

The launcher checks local Docker Desktop/Linux, refuses remote contexts, port

conflicts, foreign containers/volumes, changed configuration and unsafe port bindings.

Its Docker command environment excludes provider keys and remote-host overrides.

Docker Desktop must already be running with Linux containers and internet access for

the official image download. No registry credentials are read or displayed by Python.

Docker may use its normal private registry configuration internally.



The editor is http://localhost:5678. Create its owner account yourself in the browser

and use a different password from the property portal. No n8n account, provider OAuth,

API key, workflow, trigger, schedule or test lead is created by this release. Finish

any licence/terms screens yourself. Keep credentials out of chat and source files.

Secure cookies and n8n user management remain enabled. Use localhost in your browser;

if the browser rejects HTTP local cookies, stop and configure local TLS instead of

disabling cookie security. This is local development, not a public production service.



The host port binds only to127.0.0.1. Storage is a dedicated Docker named volume

(dpd-n8n-local-data) with ownership labels, holding SQLite, account records and n8n's

credential encryption configuration. No project directories, Docker socket, API

volumes, prospect database or agent photo folders are mounted into n8n. Its network

is separate from the property stack, with ordinary outbound internet connectivity.

No privileged mode; capabilities dropped;1GB memory/one CPU/256process limits and

bounded Docker logs. Community package installation and diagnostics are disabled.

Workflow execution payload saving is disabled; future workflows may still log their

own data, so review node behaviour before using real enquiries.



No volume is deleted, cleared or automatically migrated. An unchanged running managed

instance is checked without recreation. A stopped managed instance is NOT resumed,

because previously active workflows could run. An orphaned data volume also requires

manual recovery review. Docker's unless-stopped policy restarts a deliberately running

instance after Docker restarts; active workflows you later enable can then resume.

Use Docker Desktop to deliberately stop/resume it. Re-run step649_start.ps1 to verify a

running instance, not to force a stopped one to resume. Repeating setup never resets

accounts or rotates the n8n credential encryption key.



Step646 portal backup DOES NOT cover the separate n8n volume. Back up n8n's database

AND its credential-encryption configuration before future upgrades or migration.

There is no n8n restore automation in this release. A startup failure preserves the

volume and image pin; it does not roll back by deleting user data.



After owner setup:

1. Keep workflows inactive while preparing mapping and credentials.

2. In the property Admin Integrations page create a source bridge only when ready to

   wire that source. Save its one-time key privately in n8n Header Auth credentials.

3. Download the inactive n8n starter from that bridge. It contains a HTTP Request node,

   not a complete provider trigger. Change its URL inside Docker to

   http://host.docker.internal:3000/api/integrations/intake/YOUR-BRIDGE-ID.

   Localhost inside n8n means its own container. Docker Desktop reachability of the

   host-loopback dashboard must be checked before enabling workflows; it has not been

   live-verified in the restricted preparation session. Do not change the property

   dashboard binding to0.0.0.0 as a workaround. Do not expose either editor publicly.

4. EspoCRM base is https://crm.example.com/. Plan selected, authorised Lead

   records only. Use a dedicated restricted API user or a verified event adapter.

   A cloud webhook cannot directly reach this local computer. Native EspoCRM webhooks

   use signed array payloads; this portal bridge accepts mapped single-lead envelopes,

   so never point an unmodified EspoCRM webhook directly at the portal endpoint.

5. Gmail OAuth for owner@example.com remains a separate private setup.

   Initially select enquiry messages only. Outbound sending, mass imports, automatic

   research, calling and WhatsApp remain disconnected. No existing accounts are read.



Startup health checks confirm only the n8n engine/database readiness and safe container

settings. They do not confirm an owner account, CRM/Gmail credentials, workflow mapping

or end-to-end lead delivery. The launcher writes a nonsecret readiness report only

after its checks pass. Failed Docker permission/image/health checks report failure;

they never claim a connected integration.
