REPLY AND HUMAN CALLBACK RULES - STEP 635

This stage prepares and tests reply-handling rules only. The module is not
connected to inboxes, email/WhatsApp providers, webhooks, APIs, PostgreSQL storage,
the dashboard or a scheduler. Installation never reads a real inbox, sends an
alert, creates a live task or calls anyone. The research runner keeps running.

Selected workflow: after an attributed reply, notify the assigned owner/agent and
create a human callback review task. The requested future owner alert address is
owner@example.com; no sending account is connected. In this module,
notifications are records labelled not_connected, not delivered messages. Tasks
start needs_review, with calling_permission unknown. No AI call is triggered.

An integrating server must authenticate incoming provider events, check webhook
signatures and tenant permissions, classify the event, and match it to exactly one
existing prospect/conversation. This module does not infer a match from a name,
email address, phone number, message text or job title. A confirmed prospect link
must come from authorized server-side data or explicit manual review, never an
untrusted webhook's tenant/prospect/owner claims. Ambiguous/unmatched replies must
remain outside this workflow pending human matching. No webhook is exposed here.

Rules:
- New reply: one unsent owner notification plus a human review task. New replies
  attach to an existing open task for the same prospect instead of duplicating it.
  The existing task's assigned owner is preserved.
- Duplicate provider event in the same tenant/channel: returns unchanged state.
  Changed text, classification or prospect under that ID is a conflicting replay
  and fails for manual investigation. Channel and tenant identities are distinct.
- Opt-out: retain evidence, record a prospect-wide suppression and cancel pending
  callbacks for that prospect. Subsequent replies do not clear suppression.
- Archived prospect: no new callback task. A local notification records the block.
- Automatic reply: audit record only. Bounce: unsent delivery-issue notification,
  without a callback task. Integrators must classify opt-outs before ordinary
  replies; the module does not guess intent or classify free text with an LLM.
- Human completion/cancellation requires the assigned owner, correct tenant, a
  note and a valid aware timestamp. A later reply after task completion can create
  a new task, subject to suppression/archive checks.

Events, tasks, alerts and suppression evidence are bounded and validated. Functions
return a new snapshot without mutating their inputs. They never execute message
text or grant channel/calling permission. Rendering must escape untrusted text.
The future storage adapter MUST serialize concurrent writes and commit event,
task, notification and suppression changes in one tenant-scoped transaction with
optimistic revision checks. In-memory deduplication alone is not durable webhook
idempotency and is not sufficient for concurrent production delivery.

Before connecting live replies: implement durable transactional storage, explicit
manual matching/review UI, verified provider adapters, and separate authenticated
notification delivery with durable deduplication. Keep suppression checks at every
outbound channel. None of these integrations or sending permissions is implied by
this preparation step. No service rebuild, private key entry or restart is needed.
