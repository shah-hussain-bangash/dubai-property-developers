RESEARCH BATCH ENGINE - STEP 632

Prepared source code only. No API route, database job table, worker registration,
scheduler, dashboard button or live research job is activated by this step.
The current application and SerpApi key/quota configuration stay unchanged.

The engine advances one public source query per call, preserving candidate title,
URL, snippet, discovery timestamp, query and query role. Sources are unverified
business-profile candidates, not verified people, contacts, investors or buyers.
A query role does not establish the person's actual title or financial capacity.
Email addresses, WhatsApp status, buying ability and marketing consent are never
inferred. No messages, calls, reply notifications or callback tasks are performed.

A plan targets 1-500 unique source URLs, with up to 100 distinct bounded queries.
The default six queries cover CEO, director, entrepreneur, investor, property agent
and business owner; scope defaults to Google-indexed LinkedIn pages. It never logs
into LinkedIn or accesses private profiles. Six queries return at most 60 source
candidates with this adapter, so a 500 target is not guaranteed. More sufficiently
varied queries, source quality and search capacity are needed for larger batches.

Advance enforces existing SerpApi configuration and shared daily quota before
one request. A quota stop records the next midnight in Dubai; the engine has no
internal waiting loop and does not bypass limits. A future scheduler must decide
when to call again. Source URLs deduplicate across queries, including fragments.
Completed and exhausted batches do not make more requests. Partial results remain.

Before a provider request, the caller must durably save a request_uncertain
checkpoint, including the advanced cursor and intended attempt count. If that
save fails, no request occurs (quota reservation may already have been consumed).
After a crash or unclear response, the same query is not automatically retried.
Explicit skip_uncertain moves on without asserting that a result was obtained.
Provider errors and secrets are never copied into batch state. Pause/resume and
cancel preserve candidates; resume does not clear a pending quota wait.

INTEGRATION REQUIRED NEXT
Implement organization-scoped PostgreSQL job persistence and a per-job lock or
revision compare-and-swap. Only return updated progress after each checkpoint
commits. Do not run concurrent advances on the same batch. Then add authenticated
start/pause/resume/cancel controls and a dedicated quota-aware scheduler. The
existing generic worker retry loop must not replay an uncertain paid request.
A caller must not trust client-supplied tenant IDs, financial capacity or status.
A separate public-source/contact review stage must validate candidate relevance
and actual business contact attribution before creating saved prospect records.
The existing combined PDF exports saved prospect records, not this source queue.
No engine source is run through any of the 33 held review items.

The user's selected reply workflow remains: notify owner/agent and create a human
callback task. It requires authenticated reply ingestion and notification channels;
it must not trigger an automatic AI call. No extra provider spending is enabled.

25 offline tests include checkpoint failure, cross-tenant rejection, scope checks,
quota waits, pause/resume, duplicate removal and 500 simulated source candidates
from 50 simulated provider requests. Simulation does not consume live credits.
